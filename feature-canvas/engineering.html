01 / Engineering direction

CTO direction

Build one persistent workspace engine with two interfaces: Conversations for thinking, Agents for delegated work. Keep the domain model independent of the canvas library, AI provider and workflow framework.

This document gives high-level implementation instructions to coding agents. It accompanies the product PRD; it contains no application code, database definitions or API payload examples. Recommendations are proposed decisions, not evidence of deployed infrastructure.

Recommended starting architecture

A modular application backend, a transactional database, object storage, background workers, a provider adapter layer and one shared frontend model. Start with a small number of deployable services. Use the existing production stack wherever it already solves the problem.

  • Preserve existing prototype behavior and migrate it deliberately into durable services.
  • Ship one complete path first: mixed-input question → answer → branch → synthesis → saved output → reopen.
  • Define task, actor, run, dependency, permission and artifact identities now so agents can extend this path later.
  • Introduce libraries for difficult infrastructure; retain ownership of product semantics, permissions, context and version lineage.

Document: Engineering direction v1 · 24 October 2026 · audience: technical lead and coding agents. Library documentation checked on this date; confirm exact package versions and licenses when dependencies are pinned.

04 / Engineering direction

Data contracts to agree before coding

ConceptRequired agreement
Canvas / conversation / visual cardCanvas contains semantic objects. A thread orders messages. A card references one of those objects and stores its layout. A task or agent may have multiple visual representations without duplicated content.
Actor / task / runAn actor is a human or agent identity. A task is an objective with an assignee and completion criteria. A run is one attempt to execute work; retries create new attempts, not new agent identities.
Input and output partsOne message contains ordered typed parts: text, image, audio/transcript, file, video, code, report or HTML. Every part has independent readiness and failure state. Rendering is selected by type, not by parsing arbitrary generated HTML.
Source selectionSource ID plus immutable revision and exact selection. Text uses block identity and quote/range anchors; media uses regions/timestamps; code uses revision and line/range. Historical interpretation must survive source edits.
Artifact / reviewStable artifact identity, immutable versions and producing run. Acceptance and QA evidence target an exact version. Updated code or report invalidates prior version-specific approval.
RelationshipsBranch lineage, general reference, task dependency, delegation and handoff are different relationships. Reject cycles in execution dependencies; ordinary reference links may be cyclic.
Events / current statePersist important transitions and current projections together. Events record identity, sequence, actor, attempt and time. Use a pragmatic audit/event log; full event sourcing is not required.
Layout / draftsSave card dimensions and positions separately from content. Drafts are scoped by user, canvas and target thread; viewport and reading position are device-local.
Schema evolutionVersion durable records and exports. Add migration tests and a compatibility window. Validate imports and reference remapping before accepting data.

Ownership rule: the database is authoritative for accepted runs, approvals and server-saved content. IndexedDB is the durable client draft/cache and pending-edit queue. No provider SDK, CRDT document or graph checkpoint becomes the sole product database.

05 / Engineering direction

Canvas engine decision

Recommendation: keep the current renderer until a focused spike proves that a library meaningfully reduces risk. If the production frontend is React, React Flow is the leading candidate for connected, resizable conversation and agent cards. It provides a documented resize component and supports serializable graph/view state. Its core is MIT-licensed; paid examples and services have separate terms. See xyflow licensing, NodeResizer and save/restore.

OptionFitDecision
Existing DOM/SVG rendererClosest to the current vanilla implementation; no framework migration. We own geometry, selection, touch and accessibility maintenance.Baseline in the spike. Keep it if it meets interaction and performance gates at reasonable maintenance cost.
React Flow / xyflowCustom DOM cards, graph links, resize and minimap align with the feature. Text selection and large streaming cards still need integration work.Preferred if React is already present or an isolated React canvas boundary is justified. Do not migrate the whole site just to adopt it.
ExcalidrawEmbedded drawing/whiteboard component; MIT project. Its drawing model is less natural for rich conversation and execution records.Consider only for a later drawing artifact, not the primary workspace. Official repository.
tldrawBroad infinite-canvas SDK. Source available, but production use requires an appropriate license; it is not a permissive open-source default.Evaluate only if whiteboarding becomes central and licensing is accepted. Official license terms.

Spike gate: compare the existing renderer and the candidate using the same long report, text selection, nested branch, image, video placeholder and streaming card. Verify resizing at several zoom levels, connector re-anchoring, composer placement, keyboard controls and touch. Test 100 mixed nodes / 200 edges at representative desktop/tablet/phone sizes. Record implementation cost, bundle impact and measured latency; do not select by demo appearance.

Keep logical dimensions independent of camera zoom. Reflow text, contain media without distortion, and anchor edges to semantic sources. Make Arrange selection explicit and undoable; moving or resizing never changes AI context. The phone interface should use the shared reader/thread projection, not just reduce canvas scale. React Flow’s own performance guidance makes clear that rendering discipline remains application work.

07 / Engineering direction

Jobs and future agents: choose one durable owner

There are two distinct problems: executing retryable background work and coordinating long-running agent work across handoffs, human input and failures. Do not install multiple frameworks that all believe they own the same run lifecycle.

OptionWhere it helpsSelection rule
Existing queue + application state machineBest if the production backend already has dependable jobs. Keep run/task state and transitions in the application database.Reuse first. Validate leases, duplicate delivery, retries, cancellation and restart recovery.
BullMQBackground jobs and dependency flows in a supported backend environment. Work still needs idempotent design. Official guidance.Candidate for media/extraction and early AI jobs if it matches the stack. A queue is not the whole PM/coding/QA orchestration system.
LangGraphAgent-oriented state graphs and persisted checkpoints. Distinguishes thread checkpoints from cross-thread stores. Official persistence documentation.Candidate for future agent coordination if checkpoint/resume and bounded task flows fit. Map it behind application-owned run IDs and keep product artifacts outside graph state.
TemporalDurable workflows with event history, activities and child workflows. Official workflow overview.Evaluate when multi-day tasks, approvals and external side effects are near-term requirements and operational capacity supports it. More infrastructure than a short generation job.

Default path: use an existing reliable queue if available. Otherwise evaluate a simple worker/queue solution against the current backend. Before production agent execution, run one restart-and-approval spike to choose the durable coordinator. If Temporal is chosen, it owns outer task lifecycle; any inner model planner stays bounded. If LangGraph owns agent flow, checkpoint persistence and tool idempotency still need deliberate design. Do not launch with two competing retry or cancellation authorities.

Spike scenario: a PM creates coding and QA tasks; coding publishes a version; QA blocks on that version; a user decision pauses the flow; the worker restarts; the decision resumes only the affected work; duplicate delivery creates no second external change. Include budget exhaustion, child cancellation and a provider timeout with unknown outcome.

08 / Engineering direction

Persistence, synchronization & recovery

Prefer the current production relational database. If no backend exists, PostgreSQL plus compatible object storage is a sensible proposed baseline: relational records for ownership, tasks and versions; object storage for originals and generated media. No graph database or separate vector database is required for the first release.

  1. Local editing: write drafts and meaningful edits to IndexedDB promptly. Keep UI state responsive while synchronizing.
  2. Server acceptance: validate access and expected revision. Commit the mutation and a durable work/event record in the same transaction.
  3. Dispatch: publish pending work through a transactional outbox or equivalent reliable mechanism so a database commit cannot be stranded between persistence and enqueue.
  4. Conflict: reject stale writes with recoverable local state. Apply granular mutations to reduce needless conflicts; do not replace whole canvases blindly.
  5. Progress: events carry run identity and ordered sequence/cursor. Reconnect deduplicates and resumes; if history is unavailable, fetch the canonical current projection.
  6. Completion: persist output metadata and assets before announcing durable success. Partial output stays marked incomplete until the server confirms completion.

Delivery assumption: background work can be delivered more than once. Use stable submission and operation identities, transactional transitions and provider idempotency where supported. If a request may have succeeded but acknowledgement was lost, reconcile the provider job before retrying. When reconciliation is impossible, expose the unknown outcome rather than promise exactly-once execution.

Store large media separately. Track references from messages, drafts and context snapshots before cleanup. Deletion and retention must cover source bytes, derived transcripts, thumbnails, embeddings and backups according to policy. Browser quota failure preserves recoverable work; refresh is never the only recovery action.

09 / Engineering direction

Multimodal and provider integration

One input model, multiple provider adapters. Keep raw provider request/response shapes behind the backend. Begin with one live provider and one end-to-end path; add a second provider to prove the boundary before building a universal routing system.

PathInstructions to coding agents
Capability catalogConfigure models by supported inputs/outputs, tools, context limits and availability. Record actual model and provider per attempt. Validate on the server; UI filtering is only assistance.
Mixed inputPreserve typed text, editable voice transcript and image/file parts together. Validate uploads, authorize assets, then freeze the context manifest. Do not silently convert or omit unsupported parts.
VoiceUse browser recording for capture with explicit user activation; make transcription a separate recoverable job. Preserve typed text during transcript insertion. Decide raw-audio retention before implementing storage.
Asset ingestionUse signed upload grants and server-side completion validation. Extract/thumbnail in constrained workers, preserve source references, and distinguish stored from processed and model-ready.
Context assemblyResolve exact selected versions first; add declared history/rules/memory within budget. Summaries/retrieval disclose what was included. Never infer scope from what is on screen.
OutputsPersist structured parts and route them to trusted text/code/report/media renderers. Do not request HTML for every answer. Treat HTML as an isolated artifact with source and preview.
Image / videoUse asynchronous provider jobs where required. Store provider job IDs, poll or authenticate callbacks, deduplicate completion and move outputs into controlled storage. Each media part can fail/retry independently.
Billing / cancellationReserve/check budget before expensive work, record usage after reconciliation and enforce parent limits. Stop is best-effort; hiding a card does not cancel. Cancellation cannot reverse completed external actions.

Provider selection remains open: choose live vendors based on capability tests, latency, cost, privacy requirements and reliability. Open-source UI libraries do not supply production image/video generation. Self-hosted models are an optional later evaluation that also requires compute, serving expertise and model-specific license review.

10 / Engineering direction

PM, coding and QA collaboration

Agent collaboration extends the same messages, sources and artifacts. The scheduler reads task dependencies; the canvas displays them. A visual edge must never execute work by itself.

  1. Assignment: attach a selected branch or artifact version to a task with expected outputs, acceptance criteria and bounded authority.
  2. Planning: PM proposes tasks and dependencies. Enforce delegation depth, child count, total spend and concurrency on the server.
  3. Execution: coding agents work in isolated workspaces and produce versioned patches/artifacts. Serialize ownership or use separate branches for concurrent writers.
  4. Handoff: messages have explicit recipients and intent. Handoff is accepted/rejected/acknowledged against a specific output, not inferred from a chat mention.
  5. Verification: QA runs checks against the exact revision. Findings include reproduction and evidence. Changes invalidate earlier revision-specific approval.
  6. Decision: persist approval scope, version and requester; resume only work covered by the answer. Side-branch discussion changes a task only through an explicit Apply instruction action.
  7. Completion: distinguish run completed, task accepted, artifact integrated and deployed. Keep cancellation and pause semantics consistent across subtrees.

The agent detail tabs—Conversation, Activity, Outputs, Changes and Context—are projections of canonical records. Activity contains useful summaries, tool actions and evidence; it must not rely on private model reasoning. Parent and child runs stay visible after failure, refresh and cancellation.

Trust boundary: tools run outside the application process with scoped filesystem/network access, time/resource limits and no ambient production secrets. Read access to a canvas does not imply terminal, browser, write or publication authority. Imported source instructions cannot expand permissions.

11 / Engineering direction

Frontend performance & responsive engineering

ConcernImplementation direction
Shared stateOne domain store or projection layer feeds canvas, reader and agents. Separate transient pointer/camera state from durable content. Avoid global rerenders for each stream token or drag movement.
Resize and text selectionKeep selection anchors semantic; screen coordinates are derived. Batch geometry measurement and connector updates. One completed resize is one undo entry. Editor input must not be captured as canvas shortcuts.
Large documents / mediaUse compact previews, lazy-loaded viewers and bounded rendering. Virtualize carefully: source anchors and keyboard navigation must still resolve when a card is offscreen.
StreamingCoalesce updates for rendering and durable checkpoints; do not store every token as an independent database transaction. Retain enough progress to recover from interruption.
Small screensDesktop uses spatial view; tablet adds explicit touch modes; phone defaults to thread/agent detail. Use the same underlying identities. Keep composer above software keyboard and restore focus on close.
AccessibilitySupport keyboard equivalents for branch, multi-source selection, resize, source navigation and task controls. Announce real status changes; maintain contrast and reduced-motion behavior.
SearchStart with indexed text and metadata; preserve semantic result types and exact source navigation. Add embeddings only when retrieval quality tests show a need.

Proposed performance gate: the PRD’s 100-node / 200-edge scenario with mixed media, a long report and active streaming should maintain usable pan/resize on a representative mid-range laptop, with under 100ms local feedback as an initial target. Measure rather than claim compliance. Test phone at 390px plus tablet and desktop; include browser zoom and on-screen keyboard behavior.

Critical path: E0 → E1 → E2 → E4. E3 can progress once contracts are stable; media and agent runtime build on the same foundation. Assign owners for shared contracts and schema changes so multiple coding agents do not independently redefine them.

Every coding-agent instruction must include: objective, relevant PRD requirement, allowed modules, upstream contract versions, explicit exclusions, failure cases, verification, and required handoff artifacts. Agents should surface contract changes before implementation, preserve unrelated edits and report actual test evidence. New dependencies require a written reason; visual prototypes alone are not completion evidence.

13 / Engineering direction

Verification, operations & rollout

GateEvidence required
Domain correctnessBranches preserve exact source versions; synthesis keeps originals; layout never changes context; task dependency cycles rejected.
DurabilityCrash after database commit/before enqueue, restart during provider request, reconnect and duplicate send/callback all recover without duplicate accepted work.
IsolationCross-user/canvas access denied on server, private asset URLs scoped, HTML preview sandboxed, tool process isolated and stale approvals rejected.
Media reliabilityOne failed attachment/output does not erase successful parts. Unknown provider outcome reconciles rather than blindly restarting paid work.
Agent lifecyclePause/stop children, bound delegation, wait for input, persist approvals and resume exact attempts. QA evidence matches the reviewed revision.
User experienceReal browser screenshots/traces for zero state, mixed input, branch, resize, phone composer, artifact viewer, failure and reopening.
Operational readinessTrace run/task/attempt IDs across backend and workers; monitor queue age, save failures, provider latency, orphan jobs, spend and cancellation failures.
Release & rollbackFeature flags gate live providers/media/tools separately. Old clients remain compatible during deployment. Rollback disables new execution while preserving readable work and existing assets.

Maintain deterministic fake providers for tests and explicit demo mode; keep them separate from production behavior. Run a small controlled set of live-provider checks in staging. Add a representative context-quality set to detect wrong-source answers, omitted selected evidence and unsupported modality conversions.

Use structured traces with identifiers and redacted metadata. Do not log full prompts, transcripts, source files or credentials by default. Set storage/backup/retention policy and alerts before exposing long-running agents.
